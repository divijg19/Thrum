# v0.6.1 Observation Review

## Observation Stability

| Observation | Finding |
|---|---|
| DominantProcess | Stable. Correctly identifies resource responsibility. |
| RecentChange | Stable. Threshold asymmetry (exited vs surge/drop) fixed in v0.6.1. |
| CpuPressureTrend | Occasionally noisy on near-idle systems. Fixed in v0.6.1 (load_five < 0.01 now skips observation). |
| MemoryPressureTrend | Had second-frame false positive from PrevState::default(). Fixed in v0.6.1 (prev.mem_used == 0 guard). |
| NetworkTransferDetected | Useful but limited. No persistence filter — single-frame bursts trigger observation. Flapping is a known characteristic of threshold-only detection. |
| DiskActivityDetected | Useful but limited. Same persistence gap as NetworkTransferDetected. |

## Known Limitations

- Threshold-only activity detection (network, disk) has no hysteresis or persistence filter. A single frame above threshold fires the observation, and the next frame below threshold silences it. Adding persistence would require cross-frame state beyond the current PrevState model. Deferred to a future release where the flapping impact can be measured against real workloads.
- Priority tiers use fixed boundaries. Load and memory percentage edges (e.g., 7.999 vs 8.0) produce discontinuous priority jumps that may feel abrupt. No smoothing or interpolation is applied.
- Observations are purely within-frame for trend kinds (CpuPressureTrend, MemoryPressureTrend). No multi-frame trend smoothing exists beyond what the system load averages provide.
