# v0.6.0 Observatory Validation

## Scenario A: cargo build

**Command**: `cargo build` in Thrum project directory

**Observations produced**:
- `DominantProcess`: rustc processes dominate CPU and memory usage
- `RecentChange`: cargo/rustc process surge detected (new processes appearing)
- `CpuPressureTrend`: Emerging — load_one rises relative to load_five
- `MemoryPressureTrend`: Emerging or Stable — memory usage climbs as compilation proceeds

**Usefulness**: The Overview clearly answers "what changed" (compiler activity started), "why" (cargo build in progress), and "where to inspect" (Proc tab → rustc processes). The combination of dominant process and surge provides a complete explanatory chain.

**Limitations**: None significant — this workload is fully covered by the current observation kinds.

**Verdict**: PASS

---

## Scenario B: cargo test

**Command**: `cargo test` in Thrum project directory

**Observations produced**:
- `RecentChange`: test runner process surge (new test binaries appear)
- `DominantProcess`: test processes dominate while running
- `RecentChange`: exited processes detected as tests complete
- `CpuPressureTrend`: Emerging during test execution, Subsiding as tests finish

**Usefulness**: Process lifecycle is visible from surge through exit. The Overview explains what changed (test execution), why (test runner activity), and where to inspect (Proc tab shows individual test processes).

**Limitations**: When tests complete quickly (< refresh interval), the engine may miss short-lived processes. This is a sampler-rate limitation, not an observation engine gap.

**Verdict**: PASS

---

## Scenario C: wget (large file)

**Command**: `wget <large_file_url>`

**Observations produced**:
- `NetworkTransferDetected`: sustained network transfer above threshold
- No process-level observations (the engine has no per-process network attribution)

**Usefulness**: The Overview reports that network transfer is occurring, but cannot answer *which* process is responsible or *why*. The Net tab provides per-interface detail, but the link between network activity and process identity is missing.

**Limitations**: This is a genuine architectural gap. The current engine reasons about process behavior (CPU, memory, lifecycle). Network I/O without corresponding CPU/memory process pressure is visible as a system-level observation but not attributable to a specific process. Per-process network attribution requires deeper sysinfo integration or a different data source.

**Verdict**: KNOWN GAP

---

## Observatory Coverage Boundary

v0.6.0 reasons primarily about:

- Process behavior (CPU, memory resource consumption)
- Process dominance (which process matters most)
- Process lifecycle (new, exited, surging, dropping)
- Resource pressure trends (CPU load direction, memory usage trajectory)
- System-level activity detection (network transfer, disk I/O above threshold)

v0.6.0 does not reason about:

- Per-process network attribution (network-heavy wget is invisible at process level)
- Per-process disk attribution (disk-heavy operations without CPU pressure are invisible)
- Causal dependency chains between processes (e.g., "cargo started rustc")
- Predictive or historical patterns beyond one frame of delta
- Composite workloads where no single process dominates but aggregate activity is high

These gaps are intentional and documented. Each is a candidate for future releases if real-world usage demonstrates need.
